# Usuarios, roles y permisos (negocios, paneles y apps con empleados)
- Antes de programar, fija los roles y apúntalos en el README en una tabla: qué ve y qué hace cada uno. Base: `admin` (todo) y `empleado` (solo lo suyo); `gerente` solo si el usuario lo pide.
- Las rutas nacen cerradas: toda ruta HTML y toda `/api/...` lleva `@login_required`; las de gestión, además un decorador de rol: `def requiere_rol(*roles)` que mira `current_user.rol` y, si no toca, devuelve 403 en la API o redirige con un aviso en el HTML. Quitar el enlace del menú no protege nada: el empleado escribe la URL a mano, y un POST directo también llega: protege la ruta que escribe, no solo la que enseña el formulario.
- Solo `admin`/`gerente`: ganancias y reportes, costos (precio de compra) y márgenes, crear o borrar usuarios, crear, EDITAR y borrar productos, borrar ventas, ajustar precios y stock, exportar todo.
- El empleado vende, lista productos con precio de venta y stock (sin costo) y busca clientes. Sus ventas son las suyas: guarda `vendedor_id` en cada venta y filtra en la consulta por `current_user.id`.
- LISTA POR PANTALLA: decide estas seis, anótalas en el README y compruébalas una a una con un empleado antes de entregar.
  1. Panel de inicio: ganancias, ingresos, costos y las ventas recientes de TODOS solo para el admin; el empleado ve sus propias ventas y el stock bajo.
  2. Listas (ventas, facturas, clientes): el empleado recibe solo lo suyo; las facturas se filtran por la venta a la que pertenecen.
  3. Detalles (`/ventas/<id>`, `/facturas/<id>`, imprimir factura): si no es suya, 403/404.
  4. Productos: el empleado ve nombre, precio de venta y stock; no edita ni borra.
  5. API y JavaScript: `/api/...` aplica las mismas reglas; el costo no viaja al empleado ni en el JSON, ni en atributos `data-*`, ni en un `<script>` de la página (con `display:none` o con JavaScript el dato ya viajó): se quita en el servidor, por ejemplo con una función `a_dict(producto, rol)` que omite `precio_compra`.
  6. Reportes, usuarios y exportaciones: 403 para el empleado.
- Cuentas: solo el admin crea usuarios, desde una pantalla «Usuarios» con alta, desactivar y cambiar contraseña (sin ella no hay forma de crear empleados). Guarda `generate_password_hash(password)`, no el texto, y comprueba que el usuario creado desde esa pantalla puede entrar. `/register` abierto no existe y el rol nunca llega de un formulario anónimo. Siembra al arrancar un primer admin (por ejemplo `admin` / `admin123`) y escribe en el README y en el resumen con qué usuario entrar y cómo crear empleados.
- Flask-Login: comprueba con `check_password_hash`, llama a `login_user(usuario)` y devuelve 200 (API) o redirige al panel; sin `login_user` cada petición siguiente vuelve al login y la app parece muerta.
- PRUEBA DE MARCADORES (obligatoria, `tests/test_roles.py`): la base de pruebas es temporal y se pasa al CREAR la app (`crear_app(ruta_db)`); cambiar la URI después de crearla no la cambia y el test acaba usando y borrando la base real. El admin crea un producto con costo `7.77` y una venta de 3 unidades a 20.00 (total `60.00`) con su factura y, si la venta tiene campo de nota, la nota `NOTA-ADMIN-77`. El empleado ve la lista de clientes y vende, así que el nombre de un cliente no sirve de marcador; su propia venta de prueba es de otra cantidad (1 unidad, 20.00). Un empleado de prueba entra y recorre CADA ruta GET con un bucle (`app.url_map.iter_rules()` con GET y sin parámetros, más `/ventas/1`, `/facturas/1` y `/api/productos`): ninguna respuesta contiene `7.77`, `60.00`, `NOTA-ADMIN-77`, el número de factura del admin ni la palabra `Ganancia`. Si un marcador aparece, corrige la consulta, la plantilla o el JSON: no filtres por el texto del marcador ni por el nombre de un dato de prueba, porque eso esconde el fallo del test y lo deja en la app. Además el empleado hace POST para crear un usuario y para editar y borrar un producto: 302/403 y el dato sigue igual; el admin sí ve todo; el anónimo recibe 302/401.
- Antes de terminar, con el servidor real (`ejecutar(..., fondo=true)`) entra con el admin, crea un empleado desde la pantalla de usuarios y entra con él; pide `/reportes`, `/facturas` y `/api/productos` con cada uno. Si el empleado ve algo del admin, corrígelo antes de entregar.
